# fabric-pilot

Generated by [Software Fabric](https://github.com/smartsolutionslab/software-fabric). Every choice behind this project is recorded in `fabric.yaml` and explained in `docs/adr/`.

## Charter: Kundenportal

**Status:** approved by the owner (software-fabric#385). This repository becomes the Software Fabric's M4 pilot: a real product built on the generator, which is where the generator's gaps get found.

### The product
The Kundenportal is a B2B customer service portal.
- **Customers** (each company a tenant) raise tickets, follow their status, see their contracts and invoices, and download their documents.
- **Staff** triage the tickets. A language model suggests answers from the knowledge base and cites its sources. A person always sends the answer.

### Users
- **Now:** a demo tenant, used by smartsolutionslab staff on the deployed portal. That is what "used" means for the M4 gate until a customer joins.
- **Later:** a friendly customer joins as a second tenant. This also proves tenant isolation with real data.
- **Roles:** customer user, customer admin (manages its own tenant's users), and staff agent.

### What it is built from
The repository is regenerated (M4-40) from the released `fabric` tool with this choice set:
- profile `saas-ai-react`;
- `backend.authorization: [roles, claims]`;
- `backend.llm: azure-openai`, replacing the profile's `openai`. Local runs may use a plain OpenAI key through an OpenAI-compatible `/v1` endpoint (software-fabric#600);
- `backend.llm.extras: [rag, evals]`;
- `frontend.agent-ui: none` and `frontend.dashboards: []`: the profile's agent panel and generative dashboards are left out, because no feature needs them (owner decision, 2026-11-12).

There are six modules: `tickets`, `contracts`, `billing`, `documents`, `knowledge` and `notifications`. Each is added with `fabric add-module`, never copied. The existing `billing` module from M1 is replaced by the regenerated one.

### Where it runs
Azure Container Apps, deployed from the Aspire AppHost with hand-written IaC kept in this repository (`azd` and Bicep under `infra/`). Alongside it:
- Azure Database for PostgreSQL;
- Key Vault, for the model key and Keycloak's secrets;
- Blob Storage, for documents and attachments;
- the Azure OpenAI deployment.

The generator does not produce deployment code in M4; a `deploy.target` dimension is an M5 candidate.

### Hand-written here, not generated
The catalog has no option for these three. Each is written by hand in this repository and recorded as an M5 catalog candidate in software-fabric:
- **e-mail notifications** (feature 4);
- **document and blob storage** (features 2 and 6);
- **PDF generation** (feature 6).

### First features
Each feature is an issue in this repository, delivered by agents through the board protocol (AGENTS.md).

1. (#5) **Sign-in per tenant:** a customer user signs in and sees only their tenant's data. Staff see every tenant.
2. (#6) **Raise a ticket with attachments:** subject, description, priority and files. The files go to blob storage.
3. (#7) **Staff triage queue:** staff filter and sort open tickets across tenants, assign them and change their status.
4. (#8) **Status-change notifications:** the customer gets an e-mail and an in-app notice when their ticket changes status.
5. (#9) **Contracts with renewal dates:** customers see their contracts. Staff see upcoming renewals.
6. (#10) **Invoices as PDF:** customers see their invoices and download each one as a PDF.
7. (#11) **Knowledge base:** staff write and publish articles. Customers can read the published ones.
8. (#12) **Suggested answers with sources:** on a ticket, staff get a drafted answer retrieved from the knowledge base (RAG), with its sources linked, and they edit it before sending.
9. (#13) **Evals gate on answer quality:** the evaluations in CI fail the build when suggested-answer quality falls below the agreed threshold.
10. (#14) **Tenant admin:** a customer admin invites users to their tenant and assigns roles.

## First steps

- Point the AppHost at your Azure OpenAI resource and give it the resource's key, which stays out of the repository: `dotnet user-secrets set Parameters:azure-openai-endpoint https://<resource>.openai.azure.com --project src/AppHost` and `dotnet user-secrets set Parameters:azure-openai-api-key <key> --project src/AppHost`. The parameter `azure-openai-deployment` (`gpt-5-mini` by default) must name a deployment in that resource. Without them the host cannot call the model; the tests never need them. To run locally against OpenAI instead, with an OpenAI key, set `azure-openai-endpoint` to `https://api.openai.com/v1`, `azure-openai-api-key` to the OpenAI key and `azure-openai-deployment` to a model name: an endpoint that already ends in `/v1` is used as is.
- For the evals workflow, add the repository secret `AZURE_OPENAI_API_KEY` and the repository variable `AZURE_OPENAI_ENDPOINT`. Set the repository variable `EVALS_SCHEDULED` to `true` to run the evals weekly; they are off by default, and every run costs money.

- Create the frontend's lockfile and commit it: `cd web && pnpm install`, then commit `web/pnpm-lock.yaml`. CI installs with `--frozen-lockfile` and fails until it is there.
- Embeddings use the same Azure OpenAI resource and key, and the deployment named by the AppHost's parameter `azure-openai-embedding-deployment` (`text-embedding-3-small` by default), which must exist in that resource. Against OpenAI's `https://api.openai.com/v1`, it names an OpenAI embedding model instead.

## Agents

An agent lives in a module's Application project and a command or query runs it; its tools are the module's own commands and queries, sent through `IDispatcher`:

```csharp
public static class BillingAgent
{
    public static AIAgent Create(IChatClient model, IDispatcher dispatcher) =>
        model.AsAIAgent(
            instructions: "Answer questions about invoices. Look every invoice up; never guess.",
            name: "billing",
            tools: [DispatcherTool.For<FindInvoice>(dispatcher, "Finds an invoice by its number.")]);
}
```

`tests/Agents.Tests` runs a sample agent through a query with a stand-in model that asks for a tool call.

## Evals

`tests/Evals` scores the project's LLM use cases with the project's own model, judged by that model: relevance for every example, groundedness for those with context, and the project's own checks. Each metric's mean over a use case's examples must reach `settings.backend.llm.extras.evals.threshold` in `fabric.yaml`. A run calls the real model and costs money, so the regular tests never run it; `.github/workflows/evals.yml` does, by hand or weekly when the repository variable `EVALS_SCHEDULED` is `true`, and uploads the report.

```bash
dotnet test --project tests/Evals/Evals.csproj
dotnet tool restore && dotnet aieval report --path TestResults/evals --output TestResults/evals/report.html
```

## Retrieval

A module indexes its own records as vectors and finds the ones nearest to a question, to hand them to the model. Its index is `ModuleVectorIndex<TContext>` with the module's own DbContext, in Infrastructure:

```csharp
public sealed class InvoiceSearch(ModuleVectorIndex<BillingDbContext> invoices)
{
    public Task IndexAsync(Invoice invoice, CancellationToken cancellationToken) =>
        invoices.IndexAsync(invoice.Number, invoice.Description, cancellationToken);

    public Task<IReadOnlyList<RetrievedPassage>> FindAsync(string question, CancellationToken cancellationToken) =>
        invoices.SearchAsync(question, 5, cancellationToken);
}
```

The vectors live in PostgreSQL with pgvector (the `pgvector/pgvector` image), in the module's schema, in the table `embeddings`, which the MigrationRunner creates. `tests/Rag.Tests` indexes and searches against the AppHost's database with `FakeEmbeddingGenerator`.
