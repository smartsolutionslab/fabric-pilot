# Deploying the Kundenportal to Azure

The charter's "Where it runs": Azure Container Apps, deployed with `azd` from the hand-written Bicep in this directory.
The AppHost (`src/AppHost/AppHost.cs`) stays the description of the application; every resource here mirrors one it
declares, and the host gets the settings the AppHost gives it locally, by the same names (`infra/check.sh` compares
them in CI).

## What gets created

One resource group, `rg-<environment>`, holding:

| AppHost resource | Deployed as |
| --- | --- |
| `host` | Container App `host`, internal ingress only; reached through the web app's `/api` |
| `migrations` | Container Apps job `migrations`, run to completion after each deploy, before the host is deployed |
| `web` | Container App `web`: the SPA built with the deployed realm's authority, served by nginx, which forwards `/api` to the host |
| `keycloak` | Container App `keycloak` (production mode, `start`), its own database `keycloak`; an nginx beside it answers `/admin` only inside the environment and from `KEYCLOAK_ADMIN_ADDRESSES` |
| `postgres` / `database` | Azure Database for PostgreSQL Flexible Server (Burstable B1ms, PostgreSQL 17), database `database`, the `vector` extension allowed; private endpoint only |
| `storage` / `blobs` | Storage account; the host reaches its blob endpoint with its managed identity (no account key); private endpoint only |
| `messaging` | Container App `rabbitmq`, TCP inside the environment only |
| `mailpit` | Not deployed. The host sends through the SMTP server you name; Keycloak's realm gets its own SMTP setting |
| `azure-openai-*` parameters | Azure OpenAI resource with the deployments `gpt-5-mini` and `text-embedding-3-small` |

Besides: a Key Vault, a container registry, a Log Analytics workspace, the Container Apps environment and one
user-assigned managed identity that every app runs as. The identity may pull from the registry, read the Key Vault's
secrets and read and write blobs; nothing else.

**Network** (docs/adr/0055). A virtual network holds the Container Apps environment in one subnet and the private
endpoints of PostgreSQL, Key Vault and Storage in the other. Those three have public network access disabled: only
the environment reaches them, under their usual names. From the internet, only the web app and Keycloak answer, and
Keycloak's admin console and admin API (`/admin`) only to the addresses in `KEYCLOAK_ADMIN_ADDRESSES` (step 4).
Azure OpenAI and the container registry are still public (key and identity protect them).

**Secrets.** Key Vault holds every secret parameter the AppHost declares, under the parameter's name
(`azure-openai-api-key`, `keycloak-password`, `keycloak-user-admin-secret`, `keycloak-staff-reader-secret`, and
`smtp-password` when the SMTP server requires authentication), plus the
PostgreSQL and RabbitMQ passwords and the two connection strings that carry them. The apps reference them from Key
Vault through the identity; Key Vault answers only inside the network, so you read none of them there. The passwords and client secrets are generated by `azd` on the first `azd provision` and
kept in the azd environment's own secret store; the model's key is read from the Azure OpenAI resource by the
deployment itself. None of them is in the repository, and you never type one, but the SMTP password: that one is
your provider's, and you set it once (step 4).

## What you need

- An Azure subscription where you may create resource groups and role assignments (Owner, or Contributor plus User
  Access Administrator).
- [`azd`](https://aka.ms/azd) 1.23.13 or later, the Azure CLI (`az`), the .NET SDK `global.json` names, `jq`, `curl`
  and `bash` (on Windows: WSL or Git Bash). Docker is not needed: the .NET services are built as containers by the SDK
  and the web app by the registry (`remoteBuild`).
- An SMTP server that accepts mail from the portal over TLS: one that requires authentication (Azure Communication
  Services, most providers), with its user name and password, or a relay that needs none. Keycloak's realm sets its
  own SMTP server in its admin console, which may be the same one.

## Step by step

All commands run from the repository root.

1. **Pick the subscription and the region.** The region needs Container Apps, PostgreSQL Flexible Server, and quota
   for `gpt-5-mini` and `text-embedding-3-small` as `GlobalStandard` deployments (50k tokens per minute each by
   default). Check the quota in the Azure AI Foundry portal (Management → Quota) before you start; `swedencentral` is a
   reasonable EU choice. If the model is not offered where everything else runs, put it elsewhere with
   `azd env set AZURE_OPENAI_LOCATION <region>`.

   Register the resource providers once per subscription:

   ```sh
   az login
   az account set --subscription <subscription-id>
   for provider in Microsoft.App Microsoft.DBforPostgreSQL Microsoft.CognitiveServices Microsoft.KeyVault \
     Microsoft.ContainerRegistry Microsoft.OperationalInsights Microsoft.Storage Microsoft.ManagedIdentity \
     Microsoft.Network; do
     az provider register --namespace "$provider"
   done
   ```

2. **Sign in to azd** with the same account: `azd auth login`.

3. **Create the environment** (its name names the resource group, `rg-<name>`):

   ```sh
   azd env new kundenportal-demo
   azd env set AZURE_SUBSCRIPTION_ID <subscription-id>
   azd env set AZURE_LOCATION swedencentral
   ```

4. **Set the values** azd cannot know:

   ```sh
   azd env set SMTP_CONNECTION smtps://smtp.example.com:465        # smtp://host:587 for STARTTLS
   azd env set NOTIFICATIONS_SENDER_ADDRESS kundenportal@example.com
   azd env set TENANTS demo                                         # comma-separated; demo when unset
   azd env set KEYCLOAK_ADMIN_ADDRESSES 203.0.113.0/24              # who may open Keycloak's /admin, see below
   ```

   `KEYCLOAK_ADMIN_ADDRESSES` lists the public addresses, as comma-separated CIDR ranges (`203.0.113.7/32` for one),
   from which you administer Keycloak: its admin console, and `create-realm.sh` in step 6. Every other address outside
   the environment gets `403` on `/admin`; empty, nobody outside does. `curl -s https://ifconfig.me` prints the
   address you are seen from. A wrong range keeps Keycloak from starting (its proxy refuses the configuration): the
   revision's logs name it. To change the list later: `azd env set KEYCLOAK_ADMIN_ADDRESSES ...`, then `azd provision`.

   If the SMTP server requires authentication, set its user and password too; for a relay, leave both unset and the
   host sends without signing in:

   ```sh
   azd env set SMTP_USER_NAME <user name>                           # Azure Communication Services: the SMTP username
   azd env set SMTP_PASSWORD '<password>'                           # its password; ACS: the Entra app's client secret
   ```

   The password goes into Key Vault as `smtp-password`, and the host reads it from there (`Notifications:SmtpPassword`)
   with its user name (`Notifications:SmtpUserName`); set both or neither, or the host refuses to send. azd keeps the
   value in `.azure/<environment>/.env` on your machine, which is never committed (`.gitignore`). A wrong user name or
   password fails each notification's e-mail like an unreachable server: the host logs `AuthenticationException`,
   retries it for about a minute, then moves it to the database table `wolverine.wolverine_dead_letters` (set
   `replayable = true` on its row to deliver it again); the portal notice is still shown. To change the password
   later: `azd env set SMTP_PASSWORD '<new password>'`, `azd provision`, then restart the host as under "Later".

   `TENANTS` is the host's `Tenancy:Tenants`: each name needs the Keycloak group `/tenants/<name>`, which step 6
   creates. The model's deployments are parameters of `infra/main.bicep` with the AppHost's defaults; change one only
   together with its version (`chatModelVersion`, `embeddingModelVersion`), and remember that an embedding model of
   another size needs vector tables of that size (docs/adr/fabric/backend-llm-embeddings-azure-openai.md).

5. **Provision and deploy:** `azd up`. It creates everything above (about 15 minutes, most of it PostgreSQL), then
   deploys `migrations` and runs the job to completion (`infra/scripts/run-migrations.sh`), then `host`, then `web`.
   At the end it prints the web app's address; `azd env get-value WEB_URL` prints it again.

   If the first `azd up` stops on a container app that cannot read a Key Vault secret, the identity's role assignment
   or the private endpoint's DNS record had not reached Key Vault yet. Run `azd up` again.

   Then check that the admin console is closed to everyone else, from an address **not** in
   `KEYCLOAK_ADMIN_ADDRESSES` (a phone off Wi-Fi will do), and open to you from a listed one:

   ```sh
   curl -s -o /dev/null -w '%{http_code}\n' "$(azd env get-value KEYCLOAK_URL)/admin/master/console/"   # 403 unlisted, 200 listed
   curl -s -o /dev/null -w '%{http_code}\n' "$(azd env get-value KEYCLOAK_URL)/realms/master"           # 200 from anywhere
   ```

6. **Create the realm**, once:

   ```sh
   bash infra/keycloak/create-realm.sh
   ```

   Run it from an address in `KEYCLOAK_ADMIN_ADDRESSES`; it reads the client secrets from the azd environment, not from
   Key Vault. It creates the realm `fabric-pilot` in the deployed Keycloak from the local one (`src/AppHost/realms/realm.json`,
   through `infra/keycloak/deployed-realm.jq`): the roles, the clients `fabric-pilot-web` (redirect URI: the web
   app), `fabric-pilot-api`, `fabric-pilot-user-admin` and `fabric-pilot-staff-reader` with the secrets Key Vault holds
   for the host, the service accounts' roles (`manage-users`; `query-users` and `view-realm`), the token mappers, the
   user profile, and a group `/tenants/<tenant>` per tenant in `TENANTS`. It creates no users, and leaves an existing
   realm untouched. `infra/keycloak-user-admin.md` describes the same clients by hand; check them there.

   Then, in the admin console (`<KEYCLOAK_URL>/admin`, from a listed address, user `admin`; the password is
   `azd env config get infra.parameters.keycloakPassword`):
   - **Realm `fabric-pilot` → Realm settings → Email**: the realm's SMTP server, so invitations and password resets
     arrive (`infra/keycloak-user-admin.md`, step 5). Save, then **Test connection**.
   - Optional: **Realm settings → Themes, Localization** for the customer-facing login page.

   The `admin` user in the master realm is Keycloak's temporary bootstrap administrator. Create a permanent
   administrator in the master realm and delete `admin` once you have signed in with it.

7. **Create the demo tenant's first users**, in the realm `fabric-pilot` → **Users → Add user**:
   - **A staff member**: username and e-mail, e-mail verified; **Role mapping → Assign role → `staff`**. Staff read
     every tenant's tickets and are offered as assignees.
   - **The demo tenant's admin**: username and e-mail, e-mail verified, **Join groups → `/tenants/demo`**; **Role
     mapping → Assign role → `customer-admin`**.

   For each, either **Credentials → Set password** with *Temporary* on (hand it over out of band), or **Send email →
   Update Password** (needs the realm's SMTP from step 6). From then on the demo tenant's admin invites the tenant's
   further users from the portal (Identity), and Keycloak mails each invitation.

   Another tenant later: add it to `TENANTS` (`azd env set TENANTS demo,acme`), run `azd provision`, and create the
   group `/tenants/acme` in the admin console (the script only creates groups for a new realm).

8. **Sign in** at `WEB_URL` as the demo tenant's admin; raise a ticket with an attachment, and as the staff member
   find it in the triage queue.

## Later

- **A new version of the code:** `azd deploy` (or one service: `azd deploy host`). Deploying `migrations` runs the job
  again before the host is deployed.
- **A change under `infra/`:** `azd provision`, then `azd deploy`. `bash infra/check.sh` (with the Bicep CLI on the
  path, or `BICEP=<path>`) runs the same checks as CI.
- **Logs:** the Log Analytics workspace, table `ContainerAppConsoleLogs_CL` (the job's under `ContainerJobName_s`).
- **Rotating a Keycloak client's secret:** the value lives in the azd environment. `azd env config unset
  infra.parameters.keycloakUserAdminSecret` (or `...keycloakStaffReaderSecret`), `azd provision` (a new one is
  generated and written to Key Vault), set the same value on the client through Keycloak's admin REST API (the console
  can only generate one), then restart the host: `az containerapp revision restart --name host --resource-group
  rg-<environment> --revision <active revision>`.
- **Moving a deployment into the network** (one made before docs/adr/0055, such as the first demo). A Container Apps
  environment cannot join a subnet after it is created, so the apps, the job and the environment are made again; the
  database, Key Vault, Storage and everything in them stay. Keycloak's sessions end; nothing else is lost (the broker
  keeps no messages, the outbox of docs/adr/fabric/backend-bus-library-wolverine.md is in PostgreSQL). The environment's new default domain changes `WEB_URL` and
  `KEYCLOAK_URL`: tell the tenants the new address.

  ```sh
  azd env set KEYCLOAK_ADMIN_ADDRESSES <your range>
  group=$(azd env get-value AZURE_RESOURCE_GROUP)
  for app in web host keycloak rabbitmq; do az containerapp delete --name "$app" --resource-group "$group" --yes; done
  az containerapp job delete --name migrations --resource-group "$group" --yes
  az containerapp env delete --name "$(azd env get-value AZURE_CONTAINER_APPS_ENVIRONMENT_NAME)" --resource-group "$group" --yes
  azd up
  az postgres flexible-server firewall-rule delete --resource-group "$group" \
    --name "$(az postgres flexible-server list --resource-group "$group" --query [0].name --output tsv)" \
    --rule-name AllowAllAzureServicesAndResourcesWithinAzureIps --yes   # moot with public access off; removes it
  ```

  Then check `/admin` as after step 5, and in the admin console set the realm `fabric-pilot`'s client
  `fabric-pilot-web` to the new `WEB_URL`, as `create-realm.sh` would have (it leaves an existing realm alone):
  **Valid redirect URIs** `<WEB_URL>/*` and **Web origins** `<WEB_URL>`, replacing the old ones. Sign in at the new
  `WEB_URL`, open a ticket's attachment (Storage) and invite a user as a tenant admin (the host's call to `/admin`).
- **Removing everything:** `azd down --purge` (Key Vault and the Azure OpenAI resource are soft-deleted otherwise, and
  block the names for a week).
